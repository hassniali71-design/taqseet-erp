# تشغيل HESBA لعميل واحد على خطة Supabase المجانية (بند 78)

> القرار المعتمد: نسخة واحدة لعميل واحد، مشروع Supabase منفصل على الخطة المجانية، بدون اشتراكات مدفوعة.
> **مفيش ضمان إن الخطة المجانية تكفي سنة كاملة** — الضمان الوحيد إننا نقيس كل أسبوع ونتصرف بدري.

## 1) حدود الخطة المجانية اللي تهمّنا

الأرقام دي من مصادر خارجية متفقة عليها (صفحة Supabase الرسمية ماكانتش متاحة من بيئة الفحص) —
**اتأكد منها مرة في supabase.com/pricing وحدّث الجدول ده**:

| الحد | المجاني (تقريبي) | ليه يهمّنا |
|---|---|---|
| حجم قاعدة البيانات | 500 MB لكل مشروع | لو اتملت، الكتابة بتقف (التحصيل والبيع) |
| النقل الشهري (Egress) | 5 GB / شهر | **أخطر حد** — كل فتحة صفحة بتنزّل جداول المحل كاملة |
| إيقاف عند عدم النشاط | بعد ~7 أيام من غير نشاط | الموقع بيقف لحد ما حد يرجّعه من اللوحة |
| النسخ الاحتياطي | مفيش نسخ يومية تلقائية | **مسؤوليتنا إحنا** — انظر القسم 3 |
| المشاريع النشطة | 2 لكل حساب | مشروع للعميل + مشروع لاختبار الاستعادة |

ملاحظات:
- إعداد **Max Rows** (Settings → Data API) مالوش علاقة بالمساحة ولا بالموارد — بيحدد بس أقصى صفوف
  في الطلب الواحد. الكود بقى صح مع أي قيمة (src/lib/fetch-all.ts). رفعه لـ10000 بيقلل عدد الطلبات
  (30 طلب → 3 لجدول فيه 30 ألف صف) لكن **مبيقللش حجم البيانات المنقولة (Egress)**.
- Egress الفعلي غالبًا أقل من حجم JSON الخام لأن الردود بتتضغط (gzip) — لازم نقيسه من اللوحة، مش نخمّنه.

## 2) المتابعة الأسبوعية (10 دقايق — نفس اليوم كل أسبوع)

1. **Supabase → Project → Usage** (أو Billing → Usage): سجّل في جدول:
   حجم القاعدة، Egress الشهر الحالي، عدد الطلبات، أي تحذير ظاهر.
2. **SQL Editor**: شغّل `supabase/diagnostics/usage-monitoring.sql` وسجّل: حجم القاعدة، أكبر 5 جداول،
   عدد الأقساط والإيصالات لكل محل.
3. **Logs → API**: أي أخطاء 4xx/5xx متكررة؟
4. اعمل **تصدير** (القسم 3) واحفظه.

### علامات الإنذار المبكر وإيه نعمل

| العلامة | المستوى | الإجراء |
|---|---|---|
| حجم القاعدة > 300 MB | إنذار | راجع أكبر الجداول؛ سجل العمليات/رسائل التذكير القديمة ممكن تتأرشف (تصدير ثم حذف بموافقة) |
| حجم القاعدة > 400 MB | خطر | قرار فوري: أرشفة بيانات قديمة أو ترقية — قبل ما الكتابة تقف |
| Egress > 50% من الحد قبل نص الشهر | إنذار | ابحث عن جهاز سايب الموقع مفتوح طول اليوم؛ قلّل الأجهزة المفتوحة؛ بلّغ المطوّر |
| Egress > 80% من الحد | خطر | المرحلة 2 (حسابات في قاعدة البيانات) بقت ضرورية؛ أو ترقية مؤقتة للشهر |
| نمو الأقساط > 5,000 صف/شهر | إنذار | الحجم بيكبر أسرع من المتوقع — خطط للمرحلة 2 |
| بطء واضح في فتح الصفحات على التابلت | إنذار | نفس المرحلة 2 |

## 3) النسخ الاحتياطي والاستعادة (مجاني بالكامل)

الخطة المجانية مفيهاش نسخ تلقائية، فعندنا طريقتين، **الاتنين لازم**:

### أ) تصدير من داخل النظام (أسبوعيًا — أي حد عنده حساب المالك)
الإعدادات ← **تحميل نسخة من البيانات** → ملف CSV فيه 21 جدول كامل (بقى بيجيب كل الصفوف مهما كان
العدد — قبل بند 78 كان بيقف عند 1000 من غير تنبيه). أول الملف فيه **عدد صفوف كل جدول** — قارنه
بنتيجة الاستعلام 3 في usage-monitoring.sql للتأكد إن النسخة كاملة.
ده بيحفظ البيانات للقراءة/المراجعة، لكنه **مش نسخة تتسترجع بضغطة**.

### ب) نسخة قاعدة بيانات حقيقية تتسترجع (أسبوعيًا + قبل أي migration)
على جهاز المطوّر (PostgreSQL client أو Supabase CLI — مجانيين):
```bash
# Connection string من: Project Settings → Database → Connection string (URI) — متحطوش في Git
pg_dump "<connection-string>" --no-owner --no-privileges -Fc -f hesba-YYYY-MM-DD.dump
```
احفظ الملف في مكانين (جهازك + Google Drive). **الملف فيه كل بيانات العميل — عامله كسرّ.**

### ج) تجربة الاستعادة (مرة كل شهر — من غير ما نلمس قاعدة العميل)
1. مشروع Supabase مجاني تاني فاضي (مشروع الاختبار).
2. طبّق عليه migrations من 0001 لآخر واحد بالترتيب.
3. `pg_restore --data-only --no-owner -d "<test-connection-string>" hesba-YYYY-MM-DD.dump`
4. شغّل usage-monitoring.sql على الاتنين وقارن عدد الصفوف.
لو العدد اتطابق → النسخة صالحة. ده الدليل الوحيد إن الاستعادة هتنفع وقت الطوارئ.

## 4) لو المشروع اتوقف (Paused)
- السبب المعتاد: 7 أيام من غير نشاط. مهمة التذكيرات اليومية (Cloudflare Cron 06:00 UTC) بتقرا من
  القاعدة كل يوم، فغالبًا بتمنع الإيقاف — **مش مضمون**، ومحل شغال يوميًا مش هيوصل للحد ده أصلًا.
- الاستعادة: Supabase Dashboard → المشروع → **Restore project**. بياخد دقايق، والبيانات بتفضل.
- بعد الاستعادة: افتح الموقع، سجّل دخول، وافتح عقد واحد للتأكد.

## 5) قبل أي migration على قاعدة العميل
1. نسخة pg_dump (القسم 3-ب).
2. جرّب الـmigration على مشروع الاختبار الأول.
3. طبّقه على قاعدة العميل من SQL Editor (الملف كله، من غير تظليل جزء).
4. شغّل الاستعلام 4 في usage-monitoring.sql للتأكد إنه اتطبّق.

## 6) الـmigrations المتاحة وحالتها (حدّث الجدول ده بعد كل تطبيق)

| الملف | الغرض | الحالة |
|---|---|---|
| 0025 | الدفتر + تعديل/حذف التحصيل | متطبّق (مؤكد 2026-10-25) |
| 0026/0027 | حذف عميل نهائي كامل | 0027 متطبّق (مؤكد) |
| 0028 | التحديث اللحظي بين الأجهزة | غير مؤكد |
| 0029 | تحصيل ذري محمي من التكرار والتزامن | **محتاج موافقة** — مش متطبّق |
| 0030 | فهارس الجلب على صفحات | **محتاج موافقة** — مش متطبّق |

## 7) المرحلة 2 (لما المؤشرات تقول)
الحل الدائم لحد Egress وبطء الأجهزة الضعيفة: الحسابات والتجميع في قاعدة البيانات (Views/RPC)،
وصفحة العقد تجيب عقدها بس، والقوايم تتحمّل 50 صف بصفحات من السيرفر. مش مطلوب دلوقتي — ابدأ فيه
لما أي علامة "إنذار" في القسم 2 تظهر مرتين ورا بعض.
